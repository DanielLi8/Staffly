## Roles & access control (Phase 2)

- Roles are `STAFF`, `ADMIN` (see `enum Role` in `prisma/schema.prisma`; renamed from `SCHEDULER` to `ADMIN` via `ALTER TYPE "Role" RENAME VALUE`, see `prisma/migrations/20260830010147_rename_scheduler_to_admin`). `ADMIN` = merged scheduler+admin (the `/admin` area); `STAFF` = bidding (`/worker`). A third role, `UNIT_CLERK` (read-only, scoped to one department via `User.clerkDepartmentId`, the `/clerk` area), existed through Phase 5 and was removed - dropping an enum value requires recreating the `Role` type (no safe `ALTER TYPE ... DROP VALUE`), see `prisma/migrations/20260830190000_remove_unit_clerk_role`. `tests/authz/role-migration.test.ts` is a test of history (the Phase 2 migration) and predates the removal, so it still references the old three-role shape on purpose.
- Authorization layer lives in `src/lib/authz/` and is pure (no DB/session) so it is unit-testable. `shiftReadScope(actor)` returns a `Prisma.ShiftWhereInput`; `shiftListWhere(actor, callerFilter)` AND-s the scope in **unconditionally** so a caller filter can never widen it. Any new schedule/shift-list query MUST go through `shiftListWhere` - this is the security boundary, enforced at the data layer, not the UI. Access-control tests: `tests/authz/`.
- Build `Actor` from a session with `actorFromSession`/`requireActor` in `src/lib/auth.ts`. Role→home routing lives in `src/middleware.ts` and `src/app/page.tsx`.
- **ADMIN "view as" toggle** (`src/lib/view-mode.ts`, pure): an ADMIN can preview the app as a worker via a `staffly-view-mode` cookie (`ADMIN`|`WORKER`), set only by `setViewMode` (`src/app/actions/view-mode.ts`, itself gated by `requireActor("ADMIN")`). STAFF has no view-mode concept and always resolves to `WORKER` (`resolveViewMode`) regardless of any stray cookie. This is a separate axis from `Role` - it never touches `shiftReadScope`/`shiftListWhere` - and gates exactly one thing: `adminRouteRedirect` in `middleware.ts` blocks `/admin/*` whenever the resolved view isn't `ADMIN`, closing the URL-injection gap the same way STAFF has always been blocked (only the toggle, not a raw URL, restores access). Nav rendering follows the resolved view, not raw role - `DashboardClient` derives `variant` from it for `/profile`, and the toggle control + role badge live in `HamburgerDrawer`. Tests: `tests/lib/view-mode.test.ts` (pure routing/resolution logic), `tests/lib/view-mode-action.test.ts` (the server action).
- **Location Schedule read access** (department roster view, all roles) is a separate boundary from `shiftReadScope` on purpose - STAFF needs to see colleagues' assigned shifts department-wide, which `shiftReadScope`'s bidding-oriented STAFF branch deliberately excludes. `canViewLocationSchedule(actor, departmentId, staffMemberDepartmentIds)` (boolean gate) + `locationScheduleShiftWhere(departmentId, range)` (post-authorization filter) live alongside the existing functions in `src/lib/authz/index.ts`; a STAFF actor's department set is resolved via `resolveStaffDepartmentIds` in `src/lib/authz/staff-departments.ts` (the one DB-touching piece, kept out of the otherwise-pure `authz/index.ts`). Callers MUST call `canViewLocationSchedule` and fail closed before querying. Tests: `tests/authz/location-schedule.test.ts`.
- `classifyShiftType(startsAt)` (`src/lib/shifts/shift-type.ts`) labels a shift Day/Evening/Night from the hospital-timezone clock hour of `startsAt` only - not the full span, so a 12-hour day shift starting 07:00 stays "Day" even past 15:00. Tests: `tests/validation/shift-type.test.ts`.

## Multi-channel outreach (Phase 3)

- All outreach lives in `src/lib/outreach/`. Channels (`sms.ts`/`voice.ts`/`email.ts`/`inapp.ts`) implement the `OutreachChannel` interface (`types.ts`); the dispatcher (`index.ts`) runs every applicable channel per recipient and records one `OutreachAttempt` row each. Who is dispatched to is decided upstream by the Phase 4 cascade; the dispatcher itself is a dumb pipe.
- **Email is currently disabled** for callouts: `EMAIL_CHANNEL_ENABLED` in `index.ts` keeps `emailChannel` out of `CHANNELS`, and `dashboard.ts` filters disabled channels out of the fill-dashboard view model. `email.ts` and the templates stay in place; flipping the flag re-enables both.
- **Single accept path:** `submitBid()` in `src/lib/outreach/accept.ts` is the ONLY place a `ShiftBid` is created/updated + the scheduler notified. In-app `placeBid`, inbound SMS, and IVR all funnel through it. Acceptances are always bids (PENDING), never instant assignments.
- **Credential-optional:** every Twilio touchpoint no-ops without env vars (mirrors `src/lib/email.ts`, which builds its Resend client lazily for the same reason). `isTwilioConfigured()`/`getTwilioClient()` in `twilio.ts` gate sending; SMS/voice only fire for a number with `phoneVerifiedAt` set (Twilio Verify at `/profile`).
- **Webhooks** (`src/app/api/webhooks/twilio/*`): public + unauthenticated. Already excluded from the NextAuth `middleware` matcher (it only lists `/admin|/worker|/profile`). EVERY handler MUST call `readVerifiedTwilioForm` (validates `X-Twilio-Signature`, fails closed → 403) before any DB write. `TWILIO_AUTH_TOKEN` stays server-only. Signature URL is rebuilt from `webhookBaseUrl()` (not the proxied host) so it matches the callback URLs we hand Twilio.
- Inbound SMS resolves sender phone → verified `User`, parses a reply code (`codes.ts`: `YES <code>`=FULL, `PART <code>`=PARTIAL, bare code=FULL; carrier keywords handled) against `Shift.smsCode`. IVR pins shiftId+userId via signed query params. Tests: `tests/outreach/`.

## Tiered callout cascade + fill dashboard (Phase 4)

- The cascade lives in `src/lib/callout/`. **Postgres is the source of truth, not Inngest**: `CalloutCampaign` (one per shift, `status` = RUNNING/PAUSED/CANCELLED/FILLED/EXHAUSTED) holds all state, and every write goes through `campaign.ts`, which re-reads the row before acting. A scheduler "stop" writes CANCELLED and any running engine step reads that and no-ops. Keep it that way - it is what makes the engine swappable.
- Policy is pure and unit-tested, on purpose: `tiers.ts` (who is in which tier, seniority-ordered via `rankBySeniority`), `decide.ts` (`decideNextStep` with an injected `now`), `overtime.ts` (`projectOvertime`, a simplified weekly-hours stand-in for a real collective-agreement rule). `campaign.ts`/`dashboard.ts` hold the DB access. Tests: `tests/callout/` (`fake-db.ts` is a narrow in-memory Prisma stand-in for the service-level tests).
- Tiers widen 1 → available department staff, 2 → department staff who declared nothing (TENTATIVE counts as nothing), 3 → other departments. An overlapping `UNAVAILABLE` removes someone from the whole cascade. An empty tier is skipped immediately rather than waited out.
- `OutreachAttempt.tier` + `@@unique([shiftId, tier, userId, channel])` is the idempotency key: re-running a tier never re-contacts anyone. `dispatchOutreach(shift, recipients, { tier })` enforces it.
- **Posting delay:** outreach is NOT sent when a shift is posted. `startCalloutCampaign` only records `CalloutCampaign.tier1DispatchAt` (now + `TIER1_DISPATCH_DELAY_SECONDS`); Inngest's durable timer then calls `dispatchOpeningTier`, which re-reads the row, so a shift stopped/cancelled/filled inside the window reaches nobody. Non-null `tier1DispatchAt` means exactly "nobody contacted yet" - it is cleared when tier 1 goes out. Never re-implement this with `setTimeout`; a serverless invocation would drop it.
- **Credential-optional (mirrors Twilio):** `src/lib/inngest/client.ts` builds the client lazily and `sendCalloutEvent` no-ops without `INNGEST_EVENT_KEY`/`INNGEST_SIGNING_KEY`. Posting a shift and advance/hold/stop all work with no Inngest account; what is lost is everything needing a clock - the automatic timed escalation, and the posting delay (`startCalloutCampaign` dispatches tier 1 immediately instead). `tests/callout/no-inngest.test.ts` guards this; set the keys in any real deployment.
- **No auto-expiry.** Past the shift start an unfilled callout raises a scheduler reminder (`CALLOUT_REMINDER`) and keeps going. Never close a shift on a timer.
- Scheduler controls are `src/app/actions/callout.ts` (ADMIN-only via `requireActor` + `requireRole`); the dashboard is `src/features/callout/` on `/admin/shifts/[id]`.

## Worker availability editor (Phase 5, redesigned v3)

- `Availability` (`userId`, `startsAt`/`endsAt`, `status` AVAILABLE/UNAVAILABLE/TENTATIVE, optional `departmentId`) existed since Phase 1 for callout tiering (`src/lib/callout/tiers.ts`); v1 (Phase 5) added the create/edit UI but only on month view and one row per day, v3 widened both. `departmentId` stays null on every row this editor creates (no department scoping).
- Editing works on all three views (`/worker/schedule` only - admin's staff-mode reuse of `PersonalScheduleCalendar` never passes `editableAvailability` and stays read-only). `PersonalScheduleCalendar` (`src/features/schedule/personal-schedule-calendar.tsx`) delegates day/week/month rendering entirely to `AvailabilityEditor` (`src/features/availability/availability-editor.tsx`, client) when `editableAvailability` is passed; otherwise it renders its own plain read-only day/week/month blocks. `AvailabilityEditor` generalizes the old month-only grid over a `cells` array (`[anchor]` for day, `weekDays` for week, `monthGridDays` for month) so one tap/drag-select implementation drives all three.
- `ShiftBlock`/`PersonalScheduleShift` live in `src/features/schedule/shift-block.tsx`, not inline in `personal-schedule-calendar.tsx` - the client grid needs to render shift blocks too, and importing them from the (server) calendar component would be a circular import since that component renders the grid.
- Selection model: tap a day to toggle it in/out (this is also how one day gets removed from a drag-built range); drag across days to add the whole contiguous range. The client tracks the in-progress drag anchor/moved-flag in **refs, not state** - a mousedown immediately followed by a mouseup (a plain click, no repaint in between) must not read a stale pre-mousedown value, and state updates aren't guaranteed to have flushed by the next event.
- **Multiple blocks per day**: a day can hold several `Availability` rows, each an AVAILABLE or UNAVAILABLE time-of-day range (no more "one row per day"). `buildAvailabilityRows(days, blocks)` (`src/lib/availability/build.ts`, pure, tested in `tests/validation/availability-build.test.ts`) applies every block in the shared list to every selected day. `saveAvailability` (`src/app/actions/availability.ts`) groups the built rows by day and, per day, runs one `deleteMany` + one `createMany` **in the same transaction step** - splitting those across separate steps would let an earlier block's insert get wiped by a later block's delete for the same day.
- Proportional availability strip (v4): each cell/column renders a thin (`h-1.5`) strip (`AvailabilityBand` in `availability-editor.tsx`) whose segments are absolutely positioned by real clock-time percentage - `left% = startMinutes/1440`, `width% = (endMinutes-startMinutes)/1440` - on a `bg-neutral-100` track, so any uncovered minute shows bare track by construction rather than an even per-status split (the old v3 band gave every distinct status an equal `flex-1` share regardless of actual duration, which was materially misleading - an 8h AVAILABLE + 9h UNAVAILABLE + 7h uncovered gap rendered as a 50/50 split with the gap invisible). Reads local `Date.getHours()/getMinutes()` (not `hospitalDate`), matching this feature's local-date model above. Availability rows are always confined to one calendar day (`src/lib/availability/build.ts`), so no cross-midnight math is needed; overlapping blocks paint later-starting segments over earlier ones via DOM order. This is presentational only, computed from the same `availability` list passed in; it does not change what `tiers.ts` reads.
- Day Details panel: a plain click/keyboard-Enter on a cell sets `focusedDay` (defaults to today on load) independently of `selected` (the multi-day batch-edit set) - `handleMouseUp`'s "no movement" branch and the cell's `onKeyDown` both call `setFocusedDay` right after the existing `toggleDay`, but the drag-select path (`handleMouseDown`/`handleMouseEnter`/the window `mouseup` listener) never touches it, so dragging a range never changes or flickers the panel. When `panelMode === "empty"`, the right panel renders read-only `DayDetailsPanel` (`src/features/availability/day-details-panel.tsx`) for `focusedDay` instead of a static placeholder; its "Edit availability" button adds that day to `selected` (if not already there) and flips `panelMode` to hand off to the existing Change Availability flow - toggling a day OFF `selected` does NOT clear its Day Details, since focus and selection are independent concerns.
- Compact month/week shift chips: `CompactShiftChip` (`availability-editor.tsx`, week/month cells only - day view still renders full `ShiftBlock`) shows `department.code` + 24h `hospitalTime` range (e.g. "ER 07:00–19:00") instead of `ShiftBlock`'s full department name, which clipped illegibly at narrow cell widths. Kept local to this file rather than folded into the shared `ShiftBlock` so the admin staff-mode reuse of `PersonalScheduleCalendar` (a separate render branch, still full `ShiftBlock`) is unaffected. Month cells cap at `MONTH_CELL_SHIFT_CAP` (3) visible shifts with a "+N more" line rather than relying on scroll in an already-cramped cell.
- The grid/panel side-by-side breakpoint is `md` (768px), not `lg` - changed because a 768px tablet had visible room to spare but still stacked. `w-full md:w-80` (panel width) and both panels' own `md:min-h-[520px]` must move together with `flex-col md:flex-row` if this ever changes again, or the sidebar looks squeezed between the two breakpoints. Below `md`, tapping a day auto-`scrollIntoView`s the panel (skipped on first mount) since stacking otherwise gives no visual cue anything happened.
- `ChangeAvailabilityPanel`'s time fields pair the existing border-color signal with an inline `<p>` error (shown only once a field is non-empty and fails `parseTimeInput`) plus `aria-invalid`/`aria-describedby`, and a helper line naming why Submit is disabled (no days selected / no blocks / invalid time) - `parseTimeInput` itself (`src/lib/shifts/time.ts`) was already correct for both 12h and 24h input; the gap was purely feedback.
- Toolbar "+ New Request" (`src/features/availability/new-request-menu.tsx`) is a hand-rolled text-only dropdown (mirrors `src/components/layout/user-menu.tsx`'s click-outside/Escape pattern, the only other one in the app), rendered by `AvailabilityEditor` on all three views. This is the ONE "+ New Request" entry point for `/worker/schedule` - all three items (Change Availability, Shift Swap, Shift Giveaway) are live; there used to be a second, page-level `NewRequestMenu` (`src/features/shift-swap/new-request-menu.tsx`, deleted) offering just Swap/Giveaway that rendered alongside this one - don't reintroduce that duplication. Selecting Change Availability opens `ChangeAvailabilityPanel` (`src/features/availability/change-availability-panel.tsx`), the persistent right-side panel; Shift Swap/Giveaway open `ShiftSwapPanel` (`src/features/shift-swap/shift-swap-panel.tsx`) as an overlay. Empty-state placeholder is `AvailabilityEditor`'s own default render, not a separate component.
- Two notification paths, both via `src/lib/notifications.ts`: `notifyWorkerOfAvailabilityUpdate` (confirmation to the worker) and `notifyAdminsOfAvailabilityChange` (broadcast to every `ADMIN` - availability changes have no natural single owner the way a bid or cancellation does, so this is the first "notify every admin" helper in that file). Both use the `AVAILABILITY_UPDATED` `NotificationType`. Email is explicitly out of scope.
- Day-bucketing throughout this feature uses plain local `Date`/`isSameDay`/`format(d, "yyyy-MM-dd")`, matching `resolveScheduleRange`'s existing local-date model - not `hospitalDate`, which round-trips through the hospital timezone and would misalign the day key for a grid built from local-midnight `Date`s.
- No purple "This month/week - X hours - Scheduled" stat banner anywhere in `PersonalScheduleCalendar` - removed in v3 across all three views (editable and read-only alike), do not re-add it.

## Shift Swap / Giveaway (Phase 6 + accept/approve follow-up)

- `ShiftSwapRequest` (`requesterId`, `giveShiftId`, `kind` SWAP\|GIVEAWAY, `targetUserId`, `receiveShiftId` nullable/SWAP-only, `status` PENDING_ACCEPT→ACCEPTED/REJECTED→PENDING_APPROVAL→APPROVED/DENIED, or CANCELLED) is the data model; see `prisma/migrations/20260831001433_add_shift_swap_request`. In practice the target colleague's Accept moves the row straight from PENDING_ACCEPT to PENDING_APPROVAL (there is no separate action that persists the intermediate ACCEPTED value) - `respondedAt` is what records that they answered.
- `src/lib/shift-swap/` is pure (no DB), matching `src/lib/callout/overtime.ts`'s style: `pay-period.ts` (`payPeriodFor`/`isSamePayPeriod`, a fixed ongoing 14-day cycle anchored to Sunday 2026-08-23, classified by the HOSPITAL-timezone calendar day like `classifyShiftType`), `eligibility.ts` (`evaluateReceivingEligibility`: blocks a pickup that would exceed 75 pay-period hours or create 7 CONSECUTIVE CALENDAR DAYS - hospital-timezone - with an assigned shift), and `audit.ts` (`buildSwapReassignmentDetails`/`SWAP_REASSIGNED_ACTION` - the exact `ShiftActivity` wording an approval writes, matching the mockup verbatim: "Maria Santos → Thomas Nguyen - accepted by Thomas, approved by Sarah Chen (Admin)"). Tests: `tests/shift-swap/`.
- Requester + target-colleague actions live in `src/app/actions/shift-swap.ts`: `listMyGiveableShifts`/`listUnitSwapCandidates`/`listUnitGiveawayCandidates`/`createShiftSwapRequest` (Steps 1-3 of the requester panel, re-validating everything server-side) plus `listIncomingShiftSwapRequests`/`acceptShiftSwapRequest`/`rejectShiftSwapRequest` for the target colleague. Neither accept nor reject ever touches `Shift.assignedWorkerId`. Manager approve/deny is a SEPARATE file, `src/app/actions/shift-swap-approvals.ts` (ADMIN-only, `requireActor("ADMIN")`) - it's the only place in the whole pipeline that reassigns a shift, in one `db.$transaction` that updates `Shift.assignedWorkerId` on both shifts for a SWAP (just the give-shift for a GIVEAWAY) plus a `ShiftActivity` row per shift touched. All actions re-check both shifts are still assigned exactly as expected before writing, since either side's schedule can change while a request sits unanswered.
- UI: the requester's 3-step panel (`src/features/shift-swap/shift-swap-panel.tsx`) is wired into the single "+ New Request" menu in `src/features/availability/new-request-menu.tsx` (see above) - `AvailabilityEditor` owns the `ShiftSwapPanel` overlay state alongside `ChangeAvailabilityPanel`'s. The target's `IncomingRequestsPanel` (Accept/Reject) renders separately on `/worker/schedule`. The admin approve/deny queue is its own page, `/admin/shift-swaps` (nav link "Shift Swaps" in `staffly-header.tsx`), listing `PENDING_APPROVAL` rows via `AdminApprovalsList`.
- Notifications (`src/lib/notifications.ts`, all in-app only, matching `notifyWorkerOfAvailabilityUpdate`'s "email out of scope" precedent) fire at three pipeline moments: request sent (target colleague), accepted (requester + an ADMIN broadcast reusing `notifyAdminsOfAvailabilityChange`'s "no natural single owner" pattern - a pending swap approval isn't owned by one scheduler the way a bid is), and approved/denied (both requester and colleague, via one `notifyPartiesOfShiftSwapDecision`). `notification-bell.tsx`'s `hrefForNotification` routes the six `SWAP_*` types to `/worker/schedule` or `/admin/shift-swaps` since a swap notification has no single `shiftId` to deep-link to (a SWAP touches two).
- `src/components/notifications/notification-bell.tsx`'s `fetchNotifications` checks `res.ok && Array.isArray(data)` before calling `setNotifications` - an unauthenticated/error `{ error }` response used to reach `.filter()` and crash the whole app; found while browser-verifying Phase 6.
- `/worker/schedule` is reachable by an ADMIN too (middleware doesn't fence `/worker` off from ADMIN) but `listIncomingShiftSwapRequests` requires a STAFF actor - the page guards with `session.user.role === "STAFF"` before calling it rather than letting it throw FORBIDDEN.

## Position-based callout/bid matching + Lead RN / Team Lead tag (Phase 7)

- `User.isTeamLead` (boolean, `prisma/migrations/20260915045449_add_user_is_team_lead`) is the Lead RN/Team Lead tag - independent of `position` on purpose, settable from `/admin/workers` via `setTeamLead` (`src/app/actions/workers.ts`, ADMIN-only). "Lead RN" was never a `User.position` value (position stays the base clinical position, e.g. "Registered Nurse") - it only ever existed as a free-text `DepartmentMembership.title` roster label (e.g. seed's Maria Santos/David Kim). The migration backfills `isTeamLead = true` for any user with a `title ILIKE '%lead%'` membership; `title` itself is untouched, since it's a legitimate per-department label, not something being replaced.
- **Real position-vs-role matching did not exist at all before this** - `Shift.roleNeeded` and `User.position` are both free-text and were never compared anywhere in the app; the callout cascade paged every department STAFF member regardless of clinical role (a Personal Support Worker would get an "Emergency MD" callout), and any STAFF could bid on any shift. `positionMatchesRole`/`normalizeRoleLabel` (`src/lib/shifts/role-match.ts`, pure) is the one place that comparison happens now: it strips `roleNeeded`'s trailing " (RN)"-style abbreviation, lowercases, and compares to `position` - a missing `position` fails closed (never matches, rather than defaulting to eligible). The Lead RN/Team Lead tag is deliberately NOT a parameter here; it must never affect ordinary matching, in either direction.
- Wired into `loadTierCandidates` (`src/lib/callout/campaign.ts` - now requires `shift.roleNeeded`, selects `position`, filters before tiering) and `submitBid` (`src/lib/outreach/accept.ts` - a `POSITION_MISMATCH` typed failure, same pattern as `SHIFT_CLOSED`/`DEADLINE_PASSED`, per the server-action rule below). The worker-facing "available shifts" queries (`/worker/page.tsx`, `/worker/shifts/page.tsx`) filter the same way, and `BidForm` (via `/worker/shifts/[id]/page.tsx`) shows a "doesn't match the role" message instead of the bid form for a direct link to a non-matching shift - the shift itself stays readable (unlike a `shiftReadScope` exclusion), since read access and bid eligibility are different boundaries.
- Tests: `tests/validation/role-match.test.ts` (the pure function), `tests/callout/role-matching.test.ts` (the `loadTierCandidates` regression - a Lead RN-tagged RN lands in tier 1, a mismatched position is excluded, a null position fails closed). `tests/callout/fake-db.ts`'s `FakeStaff.position` and every `tests/callout/*.test.ts` file's local `staff()` fixture helper default to `"Registered Nurse"` (matching `createFakeState`'s default shift `roleNeeded`) - a fixture staff member with no `position` override is now filtered out of every tier entirely, so this default is load-bearing for the whole suite, not just the new tests.

## Server-action validation

- **Never `throw` for user-input validation in a server action.** Next.js replaces thrown server-action errors with an opaque `digest` message in production, so a routine bad input reaches the user looking like a crash (issue #7). Return a typed failure instead - see `CreateShiftFailure` in `src/app/actions/shifts.ts` - and render it as inline field errors. `throw` stays for auth and genuinely unexpected faults; the client shows a generic retry message for those. `assignWorker`'s status guard and `editShiftTime` follow the same pattern for the same reason: a shift's status can change between page render and submit (another tab, another admin), and that's a routine race, not a crash - `AssignWorkerResult`/`EditShiftTimeFailure` are typed returns, not throws.
- **A `CANCELLED` or `CLOSED` shift is immutable** - the product rule is "the only way to change a shift past that point is to create a new request." `editShiftTime` and `assignWorker` both refuse (typed failure) once a shift leaves `OPEN`; `canCancelShift` (`src/lib/shift-status.ts`) gates the cancel button the same way. If you add a new mutation on `Shift`, check whether it needs the same guard.
- Keep the rules pure and shared so the client can block a bad submit with the *same* messages the server would return: `src/lib/shifts/validation.ts` (shift-time rules) and `src/lib/shifts/time.ts` (typeable AM/PM time entry, replacing `datetime-local`). Tests: `tests/validation/shift-times.test.ts`, `tests/features/shift-form.test.tsx`.
- `ShiftForm`'s default times (`src/features/shifts/shift-form.tsx`, `defaultTimes()`) must stay valid against `validateShiftTimes` at any wall-clock time the form is opened, not just "typical" hours - a fixed offset anchored only to `start` (e.g. `start - 12h`) can land the default bid deadline in the past once real time eats into that buffer. Anchor offsets so they hold for the worst case (start is always ~7h+ out here), or clamp against `now`.
- Never hardcode an absolute calendar date as a test fixture's shift/campaign time (e.g. `new Date("2026-08-12T...")`) - it is only "in the future" until real time catches up, then `validateShiftTimes`'s real `deadlineInPast`/`endBeforeStart` checks start rejecting it and the test fails with no code change. Compute fixture times relative to `Date.now()` instead (see `tests/callout/dispatch-delay.test.ts`, `tests/callout/no-inngest.test.ts`).
