## Roles & access control (Phase 2)

- Roles are `STAFF`, `ADMIN` (see `enum Role` in `prisma/schema.prisma`; renamed from `SCHEDULER` to `ADMIN` via `ALTER TYPE "Role" RENAME VALUE`, see `prisma/migrations/20260830010147_rename_scheduler_to_admin`). `ADMIN` = merged scheduler+admin (the `/admin` area); `STAFF` = bidding (`/worker`). A third role, `UNIT_CLERK` (read-only, scoped to one department via `User.clerkDepartmentId`, the `/clerk` area), existed through Phase 5 and was removed - dropping an enum value requires recreating the `Role` type (no safe `ALTER TYPE ... DROP VALUE`), see `prisma/migrations/20260830190000_remove_unit_clerk_role`. `tests/authz/role-migration.test.ts` is a test of history (the Phase 2 migration) and predates the removal, so it still references the old three-role shape on purpose.
- Authorization layer lives in `src/lib/authz/` and is pure (no DB/session) so it is unit-testable. `shiftReadScope(actor)` returns a `Prisma.ShiftWhereInput`; `shiftListWhere(actor, callerFilter)` AND-s the scope in **unconditionally** so a caller filter can never widen it. Any new schedule/shift-list query MUST go through `shiftListWhere` - this is the security boundary, enforced at the data layer, not the UI. Access-control tests: `tests/authz/`.
- Build `Actor` from a session with `actorFromSession`/`requireActor` in `src/lib/auth.ts`. Role→home routing lives in `src/middleware.ts` and `src/app/page.tsx`.
- **ADMIN "view as" toggle** (`src/lib/view-mode.ts`, pure): an ADMIN can preview the app as a worker via a `staffly-view-mode` cookie (`ADMIN`|`WORKER`), set only by `setViewMode` (`src/app/actions/view-mode.ts`, itself gated by `requireActor("ADMIN")`). STAFF has no view-mode concept and always resolves to `WORKER` (`resolveViewMode`) regardless of any stray cookie. This is a separate axis from `Role` - it never touches `shiftReadScope`/`shiftListWhere` - and gates exactly one thing: `adminRouteRedirect` in `middleware.ts` blocks `/admin/*` whenever the resolved view isn't `ADMIN`, closing the URL-injection gap the same way STAFF has always been blocked (only the toggle, not a raw URL, restores access). Nav rendering follows the resolved view, not raw role - `DashboardClient` derives `variant` from it for `/profile`, and the toggle control + role badge live in `HamburgerDrawer`. Tests: `tests/lib/view-mode.test.ts` (pure routing/resolution logic), `tests/lib/view-mode-action.test.ts` (the server action).
- **Location Schedule read access** (department roster view, all roles) is a separate boundary from `shiftReadScope` on purpose - STAFF needs to see colleagues' assigned shifts department-wide, which `shiftReadScope`'s bidding-oriented STAFF branch deliberately excludes. `canViewLocationSchedule(actor, departmentId, staffMemberDepartmentIds)` (boolean gate) + `locationScheduleShiftWhere(departmentId, range)` (post-authorization filter) live alongside the existing functions in `src/lib/authz/index.ts`; a STAFF actor's department set is resolved via `resolveStaffDepartmentIds` in `src/lib/authz/staff-departments.ts` (the one DB-touching piece, kept out of the otherwise-pure `authz/index.ts`). Callers MUST call `canViewLocationSchedule` and fail closed before querying. Tests: `tests/authz/location-schedule.test.ts`.
- `classifyShiftType(startsAt)` (`src/lib/shifts/shift-type.ts`) labels a shift Day/Evening/Night from the hospital-timezone clock hour of `startsAt` only - not the full span, so a 12-hour day shift starting 07:00 stays "Day" even past 15:00. Tests: `tests/validation/shift-type.test.ts`.

## Multi-channel outreach (Phase 3)

- All outreach lives in `src/lib/outreach/`. Channels (`sms.ts`/`voice.ts`/`email.ts`/`inapp.ts`) implement the `OutreachChannel` interface (`types.ts`); the dispatcher (`index.ts`) runs every applicable channel per recipient and records one `OutreachAttempt` row each. Who is dispatched to is decided upstream by the Phase 4 cascade; the dispatcher itself is a dumb pipe.
- **Email is currently disabled** for callouts: `EMAIL_CHANNEL_ENABLED` in `index.ts` keeps `emailChannel` out of `CHANNELS`, and `dashboard.ts` filters disabled channels out of the fill-dashboard view model. `email.ts` and the templates stay in place; flipping the flag re-enables both.
- **Single accept path:** `submitBid()` in `src/lib/outreach/accept.ts` is the ONLY place a `ShiftBid` is created/updated + every ADMIN notified in-app (`notifyAdminsOfNewBid`, not just the poster). In-app `placeBid`, inbound SMS, and IVR all funnel through it. Acceptances are always bids (PENDING), never instant assignments.
- **Credential-optional:** every Twilio touchpoint no-ops without env vars (mirrors `src/lib/email.ts`, which builds its Resend client lazily for the same reason). `isTwilioConfigured()`/`getTwilioClient()` in `twilio.ts` gate sending; SMS/voice only fire for a number with `phoneVerifiedAt` set (Twilio Verify at `/profile`).
- **Webhooks** (`src/app/api/webhooks/twilio/*`): public + unauthenticated. Already excluded from the NextAuth `middleware` matcher (it only lists `/admin|/worker|/profile`). EVERY handler MUST call `readVerifiedTwilioForm` (validates `X-Twilio-Signature`, fails closed → 403) before any DB write. `TWILIO_AUTH_TOKEN` stays server-only. Signature URL is rebuilt from `webhookBaseUrl()` (not the proxied host) so it matches the callback URLs we hand Twilio.
- Inbound SMS resolves sender phone → verified `User`, parses a reply code (`codes.ts`: `YES <code>`=FULL, `PART <code>`=PARTIAL, bare code=FULL, `N`/`NO`/`DECLINE` [`<code>`]=decline; carrier keywords handled) against `Shift.smsCode`. A decline with no (or an unrecognized) code resolves to the worker's ONE outstanding SMS callout (`outstandingSmsCallouts`), else asks for the code. IVR pins shiftId+userId via signed query params. Tests: `tests/outreach/`.
- **Every outbound SMS is GSM-7 and one 160-septet segment.** One non-GSM char (en dash, curly quote, `Intl`'s U+202F) flips the whole text to UCS-2 and bills ~3x. Build SMS text only in `messages.ts` (`smsBody`, `smsReplies`), which runs everything through `toGsm7` and shrinks free-text fields to fit (`gsm7.ts`; asserted in `tests/outreach/sms-messages.test.ts`). Voice/email copy is not bound by this.
- **Single decline path:** `recordDecline()` in `src/lib/outreach/decline.ts` mirrors `submitBid` - SMS `NO`, IVR key 2 and the in-app Decline button (`declineShift` in `src/app/actions/bids.ts`) all funnel through it. It writes a `ShiftDecline` row (one per shift+worker), withdraws a PENDING bid, and marks the arrival channel's `OutreachAttempt` DECLINED; a later `submitBid` deletes the decline (latest answer wins). `runTierOutreach` skips anyone with a `ShiftDecline`, so a decline stops further outreach; the fill dashboard's outreach log shows declines (including app-only decliners who were never contacted). Tests: `tests/callout/decline.test.ts`, `tests/db/decline.db.test.ts`, `e2e/worker-decline.spec.ts`.

## Tiered callout cascade + fill dashboard (Phase 4)

- The cascade lives in `src/lib/callout/`. **Postgres is the source of truth, not Inngest**: `CalloutCampaign` (one per shift, `status` = RUNNING/PAUSED/CANCELLED/FILLED/EXHAUSTED) holds all state, and every write goes through `campaign.ts`, which re-reads the row before acting. A scheduler "stop" writes CANCELLED and any running engine step reads that and no-ops. Keep it that way - it is what makes the engine swappable.
- Policy is pure and unit-tested, on purpose: `tiers.ts` (who is in which tier, seniority-ordered via `rankBySeniority`), `decide.ts` (`decideNextStep` with an injected `now`), `overtime.ts` (`projectOvertime`, a simplified weekly-hours stand-in for a real collective-agreement rule). `campaign.ts`/`dashboard.ts` hold the DB access. Tests: `tests/callout/` (`fake-db.ts` is a narrow in-memory Prisma stand-in for the service-level tests).
- Tiers widen 1 → available department staff, 2 → department staff who declared nothing (TENTATIVE counts as nothing), 3 → other departments. An overlapping `UNAVAILABLE` removes someone from the whole cascade. An empty tier is skipped immediately rather than waited out.
- `OutreachAttempt.tier` + `@@unique([shiftId, tier, userId, channel])` is the idempotency key: re-running a tier never re-contacts anyone. `dispatchOutreach(shift, recipients, { tier })` enforces it.
- **Posting delay:** outreach is NOT sent when a shift is posted. `startCalloutCampaign` only records `CalloutCampaign.tier1DispatchAt` (now + `TIER1_DISPATCH_DELAY_SECONDS`); Inngest's durable timer then calls `dispatchOpeningTier`, which re-reads the row, so a shift stopped/cancelled/filled inside the window reaches nobody. Non-null `tier1DispatchAt` means exactly "nobody contacted yet" - it is cleared when tier 1 goes out. Never re-implement this with `setTimeout`; a serverless invocation would drop it.
- **Credential-optional (mirrors Twilio):** `src/lib/inngest/client.ts` builds the client lazily and `sendCalloutEvent` no-ops without `INNGEST_EVENT_KEY`/`INNGEST_SIGNING_KEY`. Posting a shift and advance/hold/stop all work with no Inngest account; what is lost is everything needing a clock - the automatic timed escalation, and the posting delay (`startCalloutCampaign` dispatches tier 1 immediately instead). `tests/callout/no-inngest.test.ts` guards this; set the keys in any real deployment.
- **No auto-expiry.** Past the shift start an unfilled callout raises a scheduler reminder (`CALLOUT_REMINDER`) and keeps going. Never close a shift on a timer.
- **Bid acceptance is gated by shift status (and the bid window) only; never by campaign status. Stop = stop outreach.** `bidAcceptance` (`src/lib/shifts/bid-window.ts`, pure; `biddableShiftWhere` is its query mirror behind `workerAvailableShiftWhere`) is open while the shift is `OPEN` and not yet over - there is no bid deadline (column dropped) and no minimum posting lead time, so bids keep coming after the start, after "Stop outreach" (campaign `CANCELLED`) and after the tiers run out (`EXHAUSTED`), on every channel, until award or cancel. `markCampaignFilled` is therefore the one transition allowed out of a terminal campaign (`CANCELLED`/`EXHAUSTED` -> `FILLED`, keeping `endedAt`), done as conditional `updateMany`s so a racing stop/second award can't clobber it. Regression: `tests/callout/bid-after-stop.test.ts`.
- Scheduler controls are `src/app/actions/callout.ts` (ADMIN-only via `requireActor` + `requireRole`); the dashboard is `src/features/callout/` on `/admin/shifts/[id]`.

## Location Schedule grid (Phase 3+4)

- `/admin/schedule` is search-driven, not a department picker: `ScheduleSearchBox` (`src/features/location-schedule/schedule-search-box.tsx`) renders two separate, independently-scoped search inputs (staff / department, deliberately not one combined typeahead) that each call `searchScheduleTargets(query, scope)` (`src/app/actions/schedule-search.ts`), then routes to `?type=staff&id=...` (personal calendar) or `?type=department&id=...` (roster grid). Both branches share day/week/month view + anchor-date handling via `resolveScheduleRange`/`parseScheduleView`/`parseScheduleAnchor` (`src/lib/schedule/range.ts`) - `rangeEnd` is always the EXCLUSIVE end of the window, matching `locationScheduleShiftWhere`'s `{ gte, lt }` shape.
- Both `ScheduleSearchBox` inputs show a suggestion dropdown immediately on focus, before any typing, via `getDefaultScheduleTargets(scope)` (`src/app/actions/schedule-search.ts`) - departments return in full (a hospital has few enough that no cap is needed); staff cap at `STAFF_DEFAULT_LIMIT` (8) alphabetically, since typing is always available to reach anyone outside that set (the cap is a starting point, not a wall). Prefetched on mount (not lazily on first focus) so the dropdown has data the instant it opens, with no popping-in delay. `searchScheduleTargets`/`getDefaultScheduleTargets` share their DB-fetching logic via `fetchStaffResults`/`fetchDepartmentResults` in the same file. Test: `tests/features/schedule-search-box.test.tsx`.
- **Staff mode** reuses `PersonalScheduleCalendar` (`src/features/schedule/personal-schedule-calendar.tsx`), the same component `/worker/schedule` renders for the signed-in user - do not fork this again; pass a different `userId`'s shifts and `hrefFor` instead. Its optional `shiftHrefBase` prop makes shift blocks links (admin's staff mode passes `/admin/shifts/`; `/worker/schedule` omits it so STAFF's own view of their shifts stays read-only). `CalendarNav`/`primaryScheduleHeading` (`src/features/schedule/calendar-nav.tsx`) is the shared prev/next/today/view-toggle nav both this and the department mode use.
- **Department mode** goes through the one loader, `loadLocationSchedule` (`src/lib/location-schedule/load.ts`): gates on `canViewLocationSchedule` (fails closed → `notFound()`), then the roster + in-range-shifts queries, then the pure `buildLocationScheduleGrid` (`src/lib/location-schedule/grid.ts`) which buckets each shift into exactly one day column keyed by the hospital-timezone calendar date of `startsAt`. Day/week render full labels via `<LocationScheduleGrid>`; **month renders `<LocationScheduleMonthHeatmap>` instead** - a literal roster-rows x 30-day-columns table of full labels is unusable, so month is a narrow per-day shift-count badge per cell that links through to that day's full grid. Both live in `src/features/location-schedule/grid-view.tsx`.
- Cells only ever link out (`/admin/shifts/[id]`) for ADMIN - `linkHref` is omitted entirely by every other caller. `/worker/location` (STAFF, picker built only from the member's own departments via `resolveLocationScheduleDepartmentIds`, never the full department list - and omitted entirely for the common single-membership case; an ADMIN previewing the worker portal gets every department there, since middleware fences `/admin/schedule` off in WORKER view) reuses the same `loadLocationSchedule`/`<LocationScheduleGrid>` with non-linking cells; `/worker/schedule` (the personal "my shifts" calendar) is a separate component - see the availability editor below for its one addition.
- **Any shift-list query feeding a schedule/calendar view MUST exclude `CANCELLED`** (`status: { not: "CANCELLED" }`) - a cancelled shift keeps `assignedWorkerId` set, so `locationScheduleShiftWhere`, the StaffMode query in `admin/schedule/page.tsx`, and `/worker/schedule`'s own query all filter it explicitly rather than relying on `assignedWorkerId` alone.
- **Any admin-facing staff-by-name search/picker result MUST show department + position, not name alone** - two same-named `STAFF` users are otherwise indistinguishable (there is no unique display name). `ScheduleSearchStaffResult` (`src/app/actions/schedule-search.ts`) carries both `department` and `position` off `User`, rendered as `department · position` in `ScheduleSearchBox`'s `ResultRow` secondary line. If a new staff-search surface is added, apply the same pattern.

## Personal schedule: 24h time grid + availability editor (A2/B2 redesign)

- `Availability` (`userId`, `startsAt`/`endsAt`, `status` AVAILABLE/UNAVAILABLE/TENTATIVE, optional `departmentId`) drives callout tiering (`src/lib/callout/tiers.ts`, which matches by overlapping instants). The editor leaves `departmentId` null.
- **Hospital day keys, not local dates.** Schedule days are `yyyy-MM-dd` hospital-calendar keys and every instant is placed via `hospitalInstant`/`hospitalMinutesOfDay`/`addDaysToKey` (`src/lib/timezone.ts`) - never `startOfDay`/`getHours`, which follow the server or browser TZ (Vercel is UTC; the old editor saved availability at UTC wall times there). `resolveScheduleDays(view, anchor)` (`src/lib/schedule/range.ts`) gives a view's day keys plus the instant window; query it with OVERLAP (`startsAt < rangeEnd AND endsAt > rangeStart`) so a night shift from the evening before still draws its morning half. `hospitalTime(d, false)` forces `hourCycle: "h23"` - Node's ICU otherwise prints midnight as "24:00" and breaks hydration.
- Reusable, prop-driven grids in `src/features/schedule/`: `ScheduleTimeGrid` (day/week, real 24h axis, overnight segments from `segmentsByDay`/`layoutLanes` in `src/lib/schedule/time-grid.ts`, availability as background tint, amber ring for a shift outside availability) and `ScheduleMonthGrid`. Both take one person's `shifts` (+ optional `availability`), so an admin page can render anyone's; `shiftHrefBase` (a string, since a function can't cross into a client component) makes blocks links. Colors live in `schedule-visuals.tsx` (DESIGN.md "The Schedule Color Rule"); `ScheduleLegend` goes with them.
- `PersonalScheduleCalendar` is the shared shell (header row + grid). With `editable` (`/worker/schedule` only) it hands the body to `AvailabilityEditor` (`src/features/availability/availability-editor.tsx`): tap a day = Day details (`DayDetailsPanel`, deliberately no second shift card); "Set availability" swaps in `SetAvailabilityPanel`. While editing, taps (and month mouse-drags) tick days on/off and the grid highlights exactly the days a save will change.
- **Editor opens on what's SAVED, never a default** (the old one showed a hard-coded 7:00 AM-3:00 PM and Submit wiped the day's real rows). `blocksFromRows`/`selectionPattern` (`src/lib/availability/blocks.ts`) seed the choice for one day or identical days; differing days get an explicit "saving replaces all of them" notice and no preset until the worker picks. A range past the visible page is fetched first (`loadAvailabilityContext`) and Save waits for it. Regression test: `tests/features/availability-editor.test.tsx`.
- Blocks are minute ranges on a 15-minute grid; `endMinute <= startMinute` means overnight (Nights 19:00-07:00 ends next morning). Presets + labels: `blocks.ts`; day selection (range minus ticked-off days, week, weekdays/weekends): `selection.ts`; rows: `buildAvailabilityRows(dayKeys, blocks)` (`build.ts`); shift-vs-availability conflict: `conflicts.ts`. A row belongs to the hospital day it STARTS on - `saveAvailability` replaces exactly the selected days' rows in one interactive transaction and returns them so the toast's Undo (`restoreAvailability`, re-validated) can put them back.
- Notifications: `notifyWorkerOfAvailabilityUpdate` + `notifyAdminsOfAvailabilityChange` (`src/lib/notifications.ts`, in-app only) on every save and undo.
- "+ New Request" (`new-request-menu.tsx`) is the ONE request entry point on `/worker/schedule` (Set availability / Shift Swap / Shift Giveaway); don't add a second page-level menu. Swap/Giveaway open `ShiftSwapPanel` as an overlay owned by `AvailabilityEditor`.
- Layout: grid and panel sit side by side from `md` (`md:w-80 lg:w-96` panel, `md:min-h-[560px]` on both panels - change them together). Below `md` a tap on a day scrolls the panel into view. No hours/"scheduled" stat banner in this view - removed on purpose.

## Shift Swap / Giveaway (Phase 6 + accept/approve follow-up)

- `ShiftSwapRequest` (`requesterId`, `giveShiftId`, `kind` SWAP\|GIVEAWAY, `targetUserId`, `receiveShiftId` nullable/SWAP-only, `status` PENDING_ACCEPT→ACCEPTED/REJECTED→PENDING_APPROVAL→APPROVED/DENIED, or CANCELLED) is the data model; see `prisma/migrations/20260831001433_add_shift_swap_request`. In practice the target colleague's Accept moves the row straight from PENDING_ACCEPT to PENDING_APPROVAL (there is no separate action that persists the intermediate ACCEPTED value) - `respondedAt` is what records that they answered.
- `src/lib/shift-swap/` is pure (no DB), matching `src/lib/callout/overtime.ts`'s style: `pay-period.ts` (`payPeriodFor`/`isSamePayPeriod`, a fixed ongoing 14-day cycle anchored to Sunday 2026-08-23, classified by the HOSPITAL-timezone calendar day like `classifyShiftType`), `eligibility.ts` (`evaluateReceivingEligibility`: blocks a pickup that would exceed 75 pay-period hours or create 7 CONSECUTIVE CALENDAR DAYS - hospital-timezone - with an assigned shift), and `audit.ts` (`buildSwapReassignmentDetails`/`SWAP_REASSIGNED_ACTION` - the exact `ShiftActivity` wording an approval writes, matching the mockup verbatim: "Maria Santos → Thomas Nguyen - accepted by Thomas, approved by Sarah Chen (Admin)"). Tests: `tests/shift-swap/`.
- Requester + target-colleague actions live in `src/app/actions/shift-swap.ts`: `listMyGiveableShifts`/`listUnitSwapCandidates`/`listUnitGiveawayCandidates`/`createShiftSwapRequest` (Steps 1-3 of the requester panel, re-validating everything server-side) plus `listIncomingShiftSwapRequests`/`acceptShiftSwapRequest`/`rejectShiftSwapRequest` for the target colleague. Neither accept nor reject ever touches `Shift.assignedWorkerId`. Manager approve/deny is a SEPARATE file, `src/app/actions/shift-swap-approvals.ts` (ADMIN-only, `requireActor("ADMIN")`) - it's the only place in the whole pipeline that reassigns a shift, in one `db.$transaction` that updates `Shift.assignedWorkerId` on both shifts for a SWAP (just the give-shift for a GIVEAWAY) plus a `ShiftActivity` row per shift touched. All actions re-check both shifts are still assigned exactly as expected before writing, since either side's schedule can change while a request sits unanswered.
- UI: the requester's 3-step panel (`src/features/shift-swap/shift-swap-panel.tsx`) is wired into the single "+ New Request" menu in `src/features/availability/new-request-menu.tsx` (see above) - `AvailabilityEditor` owns the `ShiftSwapPanel` overlay state. The target's `IncomingRequestsPanel` (Accept/Reject) renders separately on `/worker/schedule`. The admin approve/deny queue is its own page, `/admin/shift-swaps` (nav link "Shift Swaps" in `staffly-header.tsx`), listing `PENDING_APPROVAL` rows via `AdminApprovalsList`.
- Notifications (`src/lib/notifications.ts`, all in-app only, matching `notifyWorkerOfAvailabilityUpdate`'s "email out of scope" precedent) fire at three pipeline moments: request sent (target colleague), accepted (requester + an ADMIN broadcast reusing `notifyAdminsOfAvailabilityChange`'s "no natural single owner" pattern - a pending swap approval isn't owned by one scheduler the way a bid is), and approved/denied (both requester and colleague, via one `notifyPartiesOfShiftSwapDecision`). `notification-bell.tsx`'s `hrefForNotification` routes the six `SWAP_*` types to `/worker/schedule` or `/admin/shift-swaps` since a swap notification has no single `shiftId` to deep-link to (a SWAP touches two).
- `src/components/notifications/notification-bell.tsx`'s `fetchNotifications` checks `res.ok && Array.isArray(data)` before calling `setNotifications` - an unauthenticated/error `{ error }` response used to reach `.filter()` and crash the whole app; found while browser-verifying Phase 6.
- `/worker/schedule` is reachable by an ADMIN too (middleware doesn't fence `/worker` off from ADMIN) but `listIncomingShiftSwapRequests` requires a STAFF actor - the page guards with `session.user.role === "STAFF"` before calling it rather than letting it throw FORBIDDEN.

## Position-based callout/bid matching + Lead RN / Team Lead tag (Phase 7)

- `User.isTeamLead` (boolean, `prisma/migrations/20260915045449_add_user_is_team_lead`) is the Lead RN/Team Lead tag - independent of `position` on purpose, settable from `/admin/workers` via `setTeamLead` (`src/app/actions/workers.ts`, ADMIN-only). "Lead RN" was never a `User.position` value (position stays the base clinical position, e.g. "Registered Nurse") - it only ever existed as a free-text `DepartmentMembership.title` roster label (e.g. seed's Maria Santos/David Kim). The migration backfills `isTeamLead = true` for any user with a `title ILIKE '%lead%'` membership; `title` itself is untouched, since it's a legitimate per-department label, not something being replaced.
- **Real position-vs-role matching did not exist at all before this** - `Shift.roleNeeded` and `User.position` are both free-text and were never compared anywhere in the app; the callout cascade paged every department STAFF member regardless of clinical role (a Personal Support Worker would get an "Emergency MD" callout), and any STAFF could bid on any shift. `positionMatchesRole`/`normalizeRoleLabel` (`src/lib/shifts/role-match.ts`, pure) is the one place that comparison happens now: it strips `roleNeeded`'s trailing " (RN)"-style abbreviation, lowercases, and compares to `position` - a missing `position` fails closed (never matches, rather than defaulting to eligible). The Lead RN/Team Lead tag is deliberately NOT a parameter here; it must never affect ordinary matching, in either direction.
- Wired into `loadTierCandidates` (`src/lib/callout/campaign.ts` - now requires `shift.roleNeeded`, selects `position`, filters before tiering) and `submitBid` (`src/lib/outreach/accept.ts` - a `POSITION_MISMATCH` typed failure, same pattern as `SHIFT_CLOSED`/`DEADLINE_PASSED`, per the server-action rule below). The worker-facing "available shifts" queries (`/worker/page.tsx`, `/worker/shifts/page.tsx`) filter the same way, and `BidForm` (via `/worker/shifts/[id]/page.tsx`) shows a "doesn't match the role" message instead of the bid form for a direct link to a non-matching shift - the shift itself stays readable (unlike a `shiftReadScope` exclusion), since read access and bid eligibility are different boundaries.
- Tests: `tests/validation/role-match.test.ts` (the pure function), `tests/callout/role-matching.test.ts` (the `loadTierCandidates` regression - a Lead RN-tagged RN lands in tier 1, a mismatched position is excluded, a null position fails closed). `tests/callout/fake-db.ts`'s `FakeStaff.position` and every `tests/callout/*.test.ts` file's local `staff()` fixture helper default to `"Registered Nurse"` (matching `createFakeState`'s default shift `roleNeeded`) - a fixture staff member with no `position` override is now filtered out of every tier entirely, so this default is load-bearing for the whole suite, not just the new tests.

## Live updates (bid realtime PR 2)

- Pages showing data other people change stay current by **revision polling, not push**: `<LiveRefresh topic=... initialRevision=...>` (`src/features/live/`) polls `GET /api/live/revision?topic=` (~3s on the admin shift page, only while the tab is visible; immediate check on focus/visibility/online; backoff on errors; stops for good on 400/401/403/404) and calls `router.refresh()` when the string changes. The page re-renders through its own loaders + authz, so nothing new can leak. `revalidatePath` can never reach an already-open browser - don't "fix" staleness with it. Mounted only on `/admin/shifts/[id]` so far.
- **Revisions are derived from the data** (`src/lib/live/revision.ts`: counts + max `updatedAt` per table, one SQL statement), never bumped at write sites - so webhooks, the Inngest engine and raw `updateMany`s are covered by construction. A new table/column the page renders must be added to its revision inputs (that's why `OutreachAttempt.updatedAt` exists). Compute `initialRevision` BEFORE the page's data loads.
- Topic access is `liveTopicAccess` (`src/lib/live/topics.ts`, pure): `admin-*` = ADMIN, `worker-*` = STAFF with shift topics scoped through `shiftListWhere`; anything else fails closed. A worker topic's revision must NEVER include other workers' bids (even an opaque string leaks "someone bid"). Worker/list topics are declared but have no revision source yet (the route 404s them) - add one in `liveRevision` when mounting them.
- Tests: `tests/authz/live-topics.test.ts`, `tests/live/`, `tests/features/live-refresh.test.tsx`, `tests/db/live-revision.db.test.ts` (real Postgres; `pnpm test:db`, excluded from `pnpm test`, writes to `DATABASE_URL` so only point it at a disposable seeded DB - CI's e2e job runs it), and `e2e/late-bid-live.spec.ts` (the captain's late-bid scenario, incl. a signed inbound-SMS webhook; needs `TWILIO_AUTH_TOKEN` set to any value).

## Security hardening (review S5, S7, S9-S12)

- **Redirect targets:** anything read from a `callbackUrl`-style query param goes through `safeCallbackPath` (`src/lib/safe-redirect.ts`) - same-origin paths only.
- **Rate limits are Postgres-backed, never in-memory** (a module `Map` is per Vercel instance and reset by cold starts): `ThrottleEvent` rows counted over sliding windows (`src/lib/throttle/` - pure `policy.ts` holds every limit, `store.ts` the DB access; buckets are `scope:sha256(subject)`, so no PII). Users: `src/lib/login-throttle.ts` (per account+IP, per account, per IP; a throttled `authorize` throws `LOGIN_THROTTLED` so the form can say why) and `src/lib/phone-verify-throttle.ts` (per account and per destination; every attempt counts). Tests: `tests/throttle/`.
- **One person per verified phone:** partial unique index `User_verified_phone_key` (`phone WHERE phoneVerifiedAt IS NOT NULL`) is raw SQL in `prisma/migrations/20261028120000_security_hardening` - Prisma can't model it and its diff ignores it; never drop it. Any path that sets `phoneVerifiedAt` uses `isVerifiedPhoneTaken`/`isVerifiedPhoneConflict` (`src/lib/phone-ownership.ts`).
- **Inbound Twilio webhooks that mutate** (`inbound-sms`, `voice-response`) wrap their handler in `handleWebhookOnce(key, ...)` (`src/lib/outreach/webhook-dedupe.ts`, `ProcessedWebhook` table) AFTER `readVerifiedTwilioForm`: a replayed MessageSid/CallSid gets the first TwiML back. Test fixtures must give each distinct inbound message its own SID.
- **Logs:** never log a caught provider error object - log `describeError(err)` (`src/lib/log-redact.ts`; Twilio/Resend messages carry phone numbers/emails).
- **CSP is report-only** (`next.config.mjs`, reports logged by `/api/csp-report`); enforce it by renaming the header once production logs stay quiet. A new third-party origin must be added to the policy.

## Server-action validation

- **Never `throw` for user-input validation in a server action.** Next.js replaces thrown server-action errors with an opaque `digest` message in production, so a routine bad input reaches the user looking like a crash (issue #7). Return a typed failure instead - see `CreateShiftFailure` in `src/app/actions/shifts.ts` - and render it as inline field errors. `throw` stays for auth and genuinely unexpected faults; the client shows a generic retry message for those. `assignWorker`'s status guard and `editShiftTime` follow the same pattern for the same reason: a shift's status can change between page render and submit (another tab, another admin), and that's a routine race, not a crash - `AssignWorkerResult`/`EditShiftTimeFailure` are typed returns, not throws.
- **A `CANCELLED` or `CLOSED` shift is immutable** - the product rule is "the only way to change a shift past that point is to create a new request." `editShiftTime` and `assignWorker` both refuse (typed failure) once a shift leaves `OPEN`; `canCancelShift` (`src/lib/shift-status.ts`) gates the cancel button the same way. If you add a new mutation on `Shift`, check whether it needs the same guard.
- Keep the rules pure and shared so the client can block a bad submit with the *same* messages the server would return: `src/lib/shifts/validation.ts` (shift-time rules) and `src/lib/shifts/time.ts` (typeable AM/PM time entry, replacing `datetime-local`). Tests: `tests/validation/shift-times.test.ts`, `tests/features/shift-form.test.tsx`.
- `ShiftForm`'s default times (`src/features/shifts/shift-form.tsx`, `defaultTimes()`) must stay valid against `validateShiftTimes` (start in the future) at any wall-clock time the form is opened - "tomorrow 07:00" always is; a default anchored to `now` plus a small offset would not survive a form left open.
- Never hardcode an absolute calendar date as a test fixture's shift/campaign time (e.g. `new Date("2026-08-12T...")`) - it is only "in the future" until real time catches up, then `validateShiftTimes`'s `startInPast` check or `bidAcceptance`'s "shift is over" gate starts rejecting it and the test fails with no code change (`tests/callout/fake-db.ts`'s `createFakeState` default shift is such a fixed past date - override `startsAt`/`endsAt` for anything that bids). Compute fixture times relative to `Date.now()` instead (see `tests/callout/dispatch-delay.test.ts`, `tests/callout/no-inngest.test.ts`).

## Design skills + design system

- **Read `PRODUCT.md` (users, purpose, principles, a11y bar) and `DESIGN.md` (tokens, components, named rules; `.impeccable/design.json` is its machine sidecar) before any UI work.** They describe the incumbent system - extend it, don't invent a new look.
- Project-level design skills live in `.claude/skills/`: Impeccable (`/impeccable audit|critique|polish|...`, installed with `npx impeccable install --providers=claude --scope=project`, refresh with `npx impeccable update`) and Emil Kowalski's web skills (`emil-design-eng`, `review-animations`, `mobile-native`, ...; pinned in `skills-lock.json`, refresh with `DISABLE_TELEMETRY=1 npx skills@latest update -p` - that CLI needs Node >= 22.20, the repo itself runs on Node 20). Native-only skills (`write-swift`, `animate-expo`) are deliberately not installed.
- `.impeccable/config.json` turns Impeccable telemetry, its update check, and its per-edit hook off for everyone; don't re-enable them in the shared config. The engine binary (`.claude/skills/impeccable/scripts/bin/`) is gitignored - the launcher downloads it (checksum-verified) into `~/.impeccable/` on first use. Run its detector by hand: `.claude/skills/impeccable/scripts/impeccable detect --json src`.
- Type scale is set centrally (`tailwind.config.ts` `fontFamily`/`fontSize`; DESIGN.md "Typography"): `text-xs`/`sm`/`base` are raised to 14/15/16px and `text-2xs` (13px) replaces every old `text-[9-11px]` - don't reintroduce arbitrary px sizes. Keep the fallback inside `var(--font-inter, Inter)`: a stale dev CSS chunk once left `--font-inter` undefined and a bare `var()` silently dropped the whole app to Times.
- UI invariants worth knowing before touching overlays/grids (details in `DESIGN.md` Do's/Don'ts): overlays are `z-50` (header is `z-40`) and use `useModalPanel` (`src/lib/use-modal-panel.ts`) for Escape/focus; sideways-scrolling content goes in `ScrollAreaX` (`src/components/ui/scroll-area-x.tsx`) so hidden columns are marked; text is `neutral-500`+ on white and `neutral-600`+ on tinted fills; form fields are 16px below `sm` (iOS focus-zoom); `tailwind.config.ts` sets `hoverOnlyWhenSupported`, so `hover:` never sticks on touch.
